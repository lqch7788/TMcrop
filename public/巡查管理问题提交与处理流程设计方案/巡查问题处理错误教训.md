## 教训一：状态管理不一致导致数据撕裂

### 错误位置

| 文件 | 行号 | 函数 |
|------|------|------|
| `useProblemDispatch.ts` | 397-404 | `approveProblemCompletion` |
| `MyTasksPage.tsx` | 170-178 | `handleAccept` |
| `MyTasksPage.tsx` | 186-197 | `handleReject` |

### 问题描述

问题与任务是**双向关联**的（`problem.sourceTaskId` ↔ `task.sourceProblemId`），但状态更新分散在多个 `setTasks` / `updateProblem` 调用中，没有原子性保证。

```typescript
// ❌ 错误示例：approveProblemCompletion 中的非原子操作
const approveProblemCompletion = (problemId, ...) => {
  // 1. 更新问题状态（可能成功）
  updateProblem(problemId, { status: '已处理' });

  // 2. 更新任务状态（可能失败，如 localStorage 满）
  if (problem.sourceTaskId) {
    setTasks(prev => prev.map(t =>
      t.id === problem.sourceTaskId ? { ...t, status: 'completed' } : t
    ));
  }
  // 结果：问题已关闭，任务状态未更新 → 数据撕裂
};
```

### 错误后果

- 问题显示"已处理"，但关联的任务仍显示"进行中"
- 拒绝任务时，任务从列表删除，但问题仍保留"处理中"状态
- 多标签页操作时数据不一致

### 修复方向

```typescript
// ✅ 正确做法：封装为原子操作
const approveProblemWithTask = (problemId, taskId, updates) => {
  // 1. 先更新问题
  updateProblem(problemId, updates.problem);

  // 2. 再更新任务（如果问题更新成功）
  if (updates.task) {
    setTasks(prev => prev.map(t =>
      t.id === taskId ? { ...t, ...updates.task } : t
    ));
  }

  // 3. 或者使用事务标记确保一致性
  updateProblem(problemId, {
    pendingSync: true,  // 标记需要同步
    ...updates.problem
  });
};
```

## 教训二：模块级单例状态与 localStorage 的同步陷阱

### 错误位置

`usePersistentProblems.ts:222-246`

### 问题描述

```typescript
// ❌ 问题代码
let problemsState: ProblemEntry[] = INITIAL_PROBLEMS;
let listeners: Array<(problems: ProblemEntry[]) => void> = [];

// 初始化只在首次加载时执行
try {
  const stored = localStorage.getItem(STORAGE_KEYS.DAILY_PROBLEMS);
  if (stored) {
    problemsState = JSON.parse(stored);
  }
} catch {}

// 问题：页面刷新后 problemsState 只从 INITIAL_PROBLEMS 初始化
// 没有从 localStorage 读取当前最大序号
```

### 错误后果

1. **多标签页不一致**：用户在一个标签页分派问题，另一个标签页的 `problemsState` 仍是旧数据
2. **初始化时序问题**：如果 `usePersistentProblems` 在 `localStorage` 写入前被调用，会覆盖掉新数据
3. **监听器泄漏**：`listeners.push(setProblems)` 在组件多次渲染时会累积

### 正确做法

```typescript
// ✅ 正确做法：初始化时必须同步读取 localStorage 中的最大序号
const dailyProblemCount: Record<string, number> = {};

// 从 INITIAL_PROBLEMS 初始化
INITIAL_PROBLEMS.forEach(p => {
  const dateKey = p.checkDate.replace(/-/g, '');
  dailyProblemCount[dateKey] = (dailyProblemCount[dateKey] || 0) + 1;
});

// 从 localStorage 读取并更新最大序号
try {
  const stored = localStorage.getItem(STORAGE_KEYS.DAILY_PROBLEMS);
  if (stored) {
    const storedProblems = JSON.parse(stored);
    storedProblems.forEach(p => {
      const dateKey = p.checkDate.replace(/-/g, '');
      const seq = parseInt(p.problemCode.slice(-3));
      // 【关键】取最大值，避免刷新后序号重置
      dailyProblemCount[dateKey] = Math.max(dailyProblemCount[dateKey] || 0, seq);
    });
  }
} catch {}
```

### 跨标签页同步

```typescript
// ✅ 使用 storage 事件监听器
useEffect(() => {
  const handleStorageChange = (e: StorageEvent) => {
    if (e.key === STORAGE_KEYS.DAILY_PROBLEMS) {
      forceRefresh();  // 强制刷新状态
    }
  };

  window.addEventListener('storage', handleStorageChange);
  return () => window.removeEventListener('storage', handleStorageChange);
}, []);
```

## 教训三：硬编码业务人员ID造成的数据孤岛

### 错误位置

| 文件 | 行号 | 问题 |
|------|------|------|
| `MyTasksPage.tsx` | 66 | `currentUserName = '陆启闯'` |
| `MyTasksPage.tsx` | 172 | `'U013', '陆启闯'` |
| `MyTasksPage.tsx` | 191 | `'U013', '陆启闯'` |
| `InspectionPage.tsx` | 143 | `inspectorId: 'U013'` |
| `InspectionPage.tsx` | 426 | `'U001', '系统管理员'` |

### 问题描述

所有操作用户ID都是**写死**的：

```typescript
// ❌ 错误示例
const handleAccept = (task: TaskDispatchTask) => {
  if (task.sourceProblemId) {
    acceptProblem(task.sourceProblemId, 'U013', '陆启闯');  // 硬编码
  }
};
```

### 错误后果

- 其他员工登录后，操作仍会记为"陆启闯"的操作
- 流转记录中的 `operatorName` 全是"陆启闯"，无法追溯真实操作人
- 验收弹窗中显示的 `handler` 是假数据

### 正确做法

```typescript
// ✅ 正确做法：从 localStorage 或登录态获取真实用户
const getCurrentUser = () => {
  try {
    const stored = localStorage.getItem('currentUser');
    if (stored) {
      return JSON.parse(stored);
    }
  } catch {}
  return { id: 'U001', name: '系统管理员' };  // 默认值
};

// 使用
const currentUser = getCurrentUser();
acceptProblem(task.sourceProblemId, currentUser.id, currentUser.name);
```

## 教训四：进度更新与反馈提交的状态机混乱

### 错误位置

`MyTasksPage.tsx:220-267`

### 问题描述

进度和反馈是两条独立的状态更新路径，没有统一的状态机：

```typescript
// ❌ 错误示例：进度更新只改本地
const handleProgressChange = (taskId: string, progress: number) => {
  setTasks(prev => prev.map(t =>
    t.id === taskId ? { ...t, progress } : t
  ));
  // 问题侧的 flowRecords 没有同步更新！
};

// ❌ 错误示例：反馈提交时判断逻辑混乱
if (task.progress === 100) {
  submitProblemFeedback(...);  // 异步更新问题状态
}
// 问题侧已更新，但任务侧用的是旧的 task.progress
const newStatus = task.progress === 100 ? 'waiting_acceptance' : 'in_progress';
```

### 错误后果

- 进度条拖到 100%，但 `submitProblemFeedback` 还没返回时，用户关闭弹窗
- 任务的 `status` 已是 `waiting_acceptance`，但问题的 `status` 仍是 `处理中`
- 流转记录只有 `progress` 动作，没有 `submit` 动作

### 正确做法

```typescript
// ✅ 正确做法：使用状态机统一管理
const TASK_STATUS_MACHINE = {
  pending: {
    accept: 'accepted',
    reject: null,  // 不允许
  },
  accepted: {
    start: 'in_progress',
    reject: 'rejected',
  },
  in_progress: {
    submit: 'waiting_acceptance',  // 只有 progress === 100 才能提交
    progress: 'in_progress',
    reject: 'rejected',
  },
  waiting_acceptance: {
    approve: 'completed',
    rework: 'in_progress',  // 返工回到进行中
  },
  rejected: {
    // 终态或重新分派
  },
  completed: {
    // 终态
  },
};

// 状态转换时必须更新两处
const transitionTaskAndProblem = (taskId, action, params) => {
  const task = getTask(taskId);
  const newTaskStatus = TASK_STATUS_MACHINE[task.status][action];

  if (newTaskStatus === null) {
    throw new Error(`不允许的转换: ${task.status} -> ${action}`);
  }

  // 1. 更新任务
  setTasks(prev => prev.map(t =>
    t.id === taskId ? { ...t, status: newTaskStatus, ...params.taskUpdates } : t
  ));

  // 2. 同步更新问题
  if (task.sourceProblemId && params.problemUpdates) {
    updateProblem(task.sourceProblemId, params.problemUpdates);
  }

  // 3. 记录流转
  addFlowRecord(task.sourceProblemId, action, params);
};
```

## 教训五：问题编号生成在高并发下的冲突风险

### 错误位置

`usePersistentProblems.ts:205-218`

### 问题描述

```typescript
// ❌ 错误代码
const dailyProblemCount: Record<string, number> = {};
INITIAL_PROBLEMS.forEach(p => {
  const dateKey = p.checkDate.replace(/-/g, '');
  dailyProblemCount[dateKey] = (dailyProblemCount[dateKey] || 0) + 1;
});

function generateProblemCode(dateStr: string): string {
  const dateKey = dateStr.replace(/-/g, '');
  dailyProblemCount[dateKey] = (dailyProblemCount[dateKey] || 0) + 1;
  const seq = String(dailyProblemCount[dateKey]).padStart(3, '0');
  return `PD${dateKey}${seq}`;
}
```

**问题**：页面刷新后 `dailyProblemCount` 只从 `INITIAL_PROBLEMS` 初始化，没有从 `localStorage` 读取当前最大序号。

### 错误后果

```typescript
// 场景：用户生成了 PD20260415001，然后刷新页面
// 刷新后 dailyProblemCount 从 INITIAL_PROBLEMS 重新统计
// 如果 INITIAL_PROBLEMS 中已经有 PD20260415001，会生成重复编号
dailyProblemCount['20260415'] = 1  // 重新从1开始
// 用户创建新问题 → PD20260415001（与已有重复！）
```

### 正确做法

```typescript
// ✅ 正确做法：初始化时必须同步读取 localStorage 中的最大序号
const initializeDailyCount = () => {
  const dailyCount: Record<string, number> = {};

  // 1. 从 INITIAL_PROBLEMS 统计
  INITIAL_PROBLEMS.forEach(p => {
    const dateKey = p.checkDate.replace(/-/g, '');
    const seq = parseInt(p.problemCode.slice(-3));
    dailyCount[dateKey] = Math.max(dailyCount[dateKey] || 0, seq);
  });

  // 2. 【关键】从 localStorage 读取并取最大值
  try {
    const stored = localStorage.getItem(STORAGE_KEYS.DAILY_PROBLEMS);
    if (stored) {
      const storedProblems = JSON.parse(stored);
      storedProblems.forEach(p => {
        const dateKey = p.checkDate.replace(/-/g, '');
        const seq = parseInt(p.problemCode.slice(-3));
        dailyCount[dateKey] = Math.max(dailyCount[dateKey] || 0, seq);
      });
    }
  } catch {}

  return dailyCount;
};

let dailyProblemCount = initializeDailyCount();
```

## 教训总结表

| 教训 | 严重程度 | 影响范围 | 预防措施 |
|------|---------|---------|---------|
| 状态管理不一致 | HIGH | 问题与任务数据撕裂 | 使用事务性更新或状态机 |
| 模块级单例状态同步 | HIGH | 多标签页数据不同步 | 使用 storage 事件监听 |
| 硬编码用户ID | MEDIUM | 流转记录失真 | 从登录态获取用户信息 |
| 进度/反馈状态机混乱 | MEDIUM | 状态流转不完整 | 使用状态机统一管理 |
| 编号生成冲突风险 | MEDIUM | 数据重复/覆盖 | 初始化时读取最大序号 |

## 通用检查清单

每次实现问题处理相关功能时，对照检查：

- [ ] 所有操作用户ID从登录态获取，不是硬编码
- [ ] 状态更新时同时更新问题和任务两处
- [ ] 每次状态变化都记录 flowRecords
- [ ] 编号生成初始化时读取 localStorage 最大值
- [ ] 组件支持 storage 事件同步多标签页
- [ ] 返工逻辑遵循 reworkCount 规则
