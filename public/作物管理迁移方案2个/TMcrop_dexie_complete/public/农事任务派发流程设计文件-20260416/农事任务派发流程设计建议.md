## 一、数据模型问题（需要修正）

### 1.1 `TaskFlowRecord` 和 `TaskOperationRecord` 功能重复

**问题**：方案定义了两个相似的操作记录类型，但它们实际记录的内容几乎相同。

```typescript
// TaskFlowRecord（流转记录）
interface TaskFlowRecord {
  action: 'dispatch' | 'accept' | 'reject' | ...;
  feedbackData?: { gpsLocation?, photosBefore?, ... };
}

// TaskOperationRecord（操作记录）  
interface TaskOperationRecord {
  operationType: 'accept' | 'progress' | 'complete' | ...;
  feedbackContent?: { text?, images?, voiceNote?, gpsLocation? };
}
```

**建议**：统一为一个接口 `TaskRecord`，避免数据冗余和维护混乱。

```typescript
// 统一后的操作记录
interface TaskRecord {
  id: string;
  taskId: string;
  operatorId: string;
  operatorName: string;
  action: TaskAction;  // 统一的行为枚举
  fromStatus?: TaskStatus;
  toStatus: TaskStatus;
  progress?: number;        // 操作后的进度
  comment?: string;
  actionTime: string;
  
  // 反馈内容（统一字段）
  feedback?: {
    text?: string;
    images?: string[];
    voiceNote?: string;
    gpsLocation?: { lat: number; lng: number };
    materials?: { name: string; qty: number; unit: string }[];
    laborCost?: number;
  };
  
  // 扩展字段
  extra?: Record<string, any>;
}
```

### 1.2 状态字段设计冗余

**问题**：方案中同时存在 `overtimeStatus` 和 `acceptTimeout`、`timeoutReason` 等多个字段，混乱且容易出错。

```typescript
// 当前设计（有冗余）
interface Task {
  overtimeStatus?: 'none' | 'pending_accept' | 'executing' | 'waiting_acceptance';
  acceptTimeout?: boolean;      // 冗余：超时状态已经包含了
  timeoutReason?: string;
  timeoutAction?: 'continue' | 'abandon';
  overtimeAt?: string;
}
```

**建议**：简化超时设计，用统一的方式处理：

```typescript
// 建议的超时设计
interface Task {
  // 超时状态通过计算得出，不存储
  // status === 'pending' 且 createdAt + 24h < now → 超时
  
  // 超时处理记录
  timeoutHistory?: {
    type: 'accept' | 'execution' | 'acceptance';
    occurredAt: string;
    action?: 'continued' | 'abandoned' | 'reassigned';
    reason?: string;
    handledBy?: string;
    handledAt?: string;
  }[];
  
  // 当前超时状态（仅用于UI显示）
  currentTimeout?: {
    type: 'accept' | 'execution' | 'acceptance';
    severity: 'warning' | 'overdue';
    startedAt: string;
  };
}
```

### 1.3 `requiredFeedback` 类型定义不一致

**问题**：方案中 `requiredFeedback` 的类型是数组，但操作记录中的反馈类型定义不同。

```typescript
// 方案定义
requiredFeedback?: ('gps' | 'photo_before' | 'photo_after' | 'voice' | 'material_scan')[];

// 但 TaskRecord 中的 feedback 是
feedbackContent?: {
  text?: string;
  images?: string[];  // 对应 photo_before/photo_after？
  voiceNote?: string; // 对应 voice？
  gpsLocation?: ...; // 对应 gps？
};
```

**建议**：统一反馈类型枚举：

```typescript
// 统一的反馈类型
type FeedbackType = 'text' | 'image_before' | 'image_after' | 'voice' | 'gps' | 'materials';

// 必填反馈配置
interface FeedbackRequirement {
  type: FeedbackType;
  label: string;  // "作业前照片"
  required: boolean;
}

// 任务必填项
interface Task {
  feedbackRequirements: FeedbackRequirement[];
}

// 示例配置
const defaultRequirements: FeedbackRequirement[] = [
  { type: 'gps', label: 'GPS位置', required: true },
  { type: 'image_before', label: '作业前照片', required: true },
  { type: 'image_after', label: '作业后照片', required: false },
  { type: 'voice', label: '语音备注', required: false },
];
```

## 二、状态流转问题

### 2.1 `draft` 状态是否必要？

**问题**：方案定义了 `draft`（草稿）状态，但实际业务中：
- 任务通常是创建后直接派发
- 草稿状态增加了状态复杂度

**建议**：评估是否真的需要 `draft` 状态。如果不需要，可以简化为：

```
pending → accepted → in_progress → waiting_acceptance → completed
```

如果需要草稿功能，可以改为：

```
draft → pending → accepted → in_progress → waiting_acceptance → completed
```

---

### 2.2 超时状态不应作为独立状态

**问题**：方案中将 `overtime_pending`、`overtime_executing` 作为独立状态，但这是**临时状态**，不应该和正常状态并列。

```typescript
// 当前设计（有问题）
type TaskStatus = 
  | 'pending' 
  | 'overtime_pending'  // ← 这应该是临时状态
  | 'accepted'
  | 'overtime_executing' // ← 这应该是临时状态
  | ...
```

**建议**：超时是**状态属性**，不是状态本身：

```typescript
// 正确的设计
interface Task {
  status: TaskStatus;  // pending | accepted | in_progress | waiting_acceptance | completed | rejected | failed | cancelled | abandoned
  timeout?: {
    type: 'accept' | 'execution' | 'acceptance';
    severity: 'warning' | 'critical';  // warning=即将超时，critical=已超时
    startedAt: string;
    deadline: string;
  };
}

// 判断任务是否需要关注
function getTaskAlertLevel(task: Task): 'normal' | 'warning' | 'critical' {
  if (task.timeout?.severity === 'critical') return 'critical';
  if (task.timeout?.severity === 'warning') return 'warning';
  return 'normal';
}
```

**问题**：方案提到催办，但没有详细设计：

```typescript
  remindedBy: string;         // 催办人

  message?: string;
  remindedAt: string;
  acknowledgedAt?: string;   // 被催办人确认时间
}

// 催办功能
function canSendReminder(taskId: string, userId: string): { allowed: boolean; reason?: string } {
  const lastReminder = getLastReminder(taskId);
  const todayCount = getTodayReminderCount(taskId);
  
  if (lastReminder && Date.now() - new Date(lastReminder.remindedAt).getTime() < REMINDER_CONFIG.minIntervalMinutes * 60 * 1000) {

  if (todayCount >= REMINDER_CONFIG.maxRemindersPerDay) {
    return { allowed: false, reason: '今日催办次数已达上限' };

  return { allowed: true };
}
```

## 五、技术风险与建议

### 5.1 localStorage 容量风险

**问题**：操作记录会持续增长，可能触及 localStorage 5MB 限制。

**建议**：

```typescript
// 数据管理策略
const DATA_MANAGEMENT = {
  // 操作记录保留策略
  operationRecords: {
    maxPerTask: 100,           // 每个任务最多100条记录
    archiveAfter: 90,          // 90天后归档
    archiveTo: 'indexedDB',    // 归档到 IndexedDB
  },
  
  // localStorage 容量监控
  storageMonitor: {
    warnThreshold: 0.8,        // 80%时警告
    criticalThreshold: 0.95,   // 95%时清理旧数据
  },
};

// 存储容量检查
function checkStorageCapacity(): { used: number; available: number; percentage: number } {
  let used = 0;
  for (let key in localStorage) {
    if (localStorage.hasOwnProperty(key)) {
      used += localStorage.getItem(key)?.length || 0;
    }
  }
  const limit = 5 * 1024 * 1024;  // 5MB
  return { used, available: limit - used, percentage: used / limit };
}
```

### 5.2 性能风险

**问题**：
- `useOvertimeDetection` 每次页面加载遍历所有任务
- 定时器每5分钟检测可能影响性能
- 大量操作记录渲染可能卡顿

**建议**：

```typescript
// 1. 批量处理超时检测（分片）
function checkOvertimeBatched(tasks: Task[], batchSize: number = 50): Promise<void> {
  const batches = chunk(tasks, batchSize);
  for (const batch of batches) {
    processBatch(batch);
    await sleep(10);  // 让出主线程
  }
}

// 2. 虚拟滚动（长列表）
// 工单汇总页面使用虚拟滚动处理大量数据
<VirtualList
  items={workSummaryRows}
  itemHeight={60}
  overscan={5}
>
  {row => <WorkSummaryRowComponent row={row} />}
</VirtualList>

// 3. 定时器优化
// 使用 requestIdleCallback 或 Web Worker
function scheduleOvertimeCheck() {
  if ('requestIdleCallback' in window) {
    requestIdleCallback(() => checkOvertime(), { timeout: 5000 });
  } else {
    setTimeout(() => checkOvertime(), 1000);
  }
}
```

**问题**：当前是单用户场景，但如果有多个管理员同时操作同一任务，可能产生冲突。

**建议**（预留）：

```typescript
// 乐观锁 - 版本号
interface Task {

  updatedBy: string;

// 更新时检查版本
async function updateTask(taskId: string, updates: Partial<Task>): Promise<boolean> {
  const task = await getTask(taskId);
  if (updates.version !== task.version) {
```

## 六、实施优先级细化

### 建议的细化阶段

**Phase 1: 核心状态流转（1-2天）**
1. 统一 Task 类型定义
2. 实现核心状态方法（接受/进度/验收/返工）
3. 基础验收弹窗（查看记录、通过/返工）
4. 农事任务派发页面操作列改造

**Phase 2: 超时与边界处理（1-2天）**
1. 超时检测 Hook
2. 超时状态 UI 显示
3. 撤回/取消功能
4. 进度历史展示组件

**Phase 3: 数据闭环（1天）**
1. 每日工单汇总数据聚合
2. 临时任务同步
3. 基础统计（工时、人工费）

**Phase 4: 增强功能（1-2天）**
1. 催办功能
2. 批量操作
3. 数据归档策略

**Phase 5: 优化与回归（1天）**
1. 性能优化
2. 回归测试
3. 文档更新

## 七、总结建议

| 类别 | 优先级 | 建议 |
|------|--------|------|
| **数据模型** | P0 | 统一 TaskRecord 和 TaskFlowRecord |
| **状态设计** | P0 | 超时作为属性而非独立状态 |
| **撤回/取消** | P1 | 明确权限矩阵和状态转换限制 |
| **数据闭环** | P1 | 补充生产计划关联和成本统计 |
| **技术风险** | P1 | 增加存储容量监控和分片处理 |
| **催办功能** | P2 | 设计催办间隔限制和历史记录 |
| **批量操作** | P2 | 放到后续阶段 |
