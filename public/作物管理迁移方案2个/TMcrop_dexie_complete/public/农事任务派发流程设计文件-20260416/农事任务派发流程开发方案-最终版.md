# 农事任务派发流程重构规划

## Context

农事管理模块现有5个子模块，任务是核心数据闭环节点。目前存在以下问题：
1. 农事任务派发流程缺少完整的验收和返工机制
2. 临时任务位于任务中心而非统一的任务派发管理
3. 任务数据未形成完整的闭环：任务派发 → 执行 → 进度提交 → 工单汇总
4. 各页面数据字段不统一，追溯困难

**目标**：以现有农事任务派发表格数据为基础，统一其他页面数据字段，实现任务全生命周期管理和数据闭环。

---

## 一、任务状态流转设计

### 1.1 完整状态定义

```
[草稿] → [已发布] → [已接受] → [处理中] → [待验收] → [已完成]
   ↓           ↓           ↓          ↓
 [取消]    [超时待重派] [超时未开始] [超时未提交]
                          ↓
                      [放弃执行] → [待重派]
```

**状态枚举**（9种，**超时作为状态属性而非独立状态**）：
- `draft` - 草稿（未发布）
- `pending` - 已发布（待接受）
- `accepted` - 已接受（开始处理）
- `in_progress` - 处理中（执行人正在执行）
- `waiting_acceptance` - 待验收（执行人提交100%完成）
- `completed` - 已完成（验收通过）
- `rejected` - 返工中（验收驳回，等待继续执行）
- `failed` - 任务失败（超过2次返工，需重新派发）
- `cancelled` - 已取消
- `abandoned` - 已放弃（执行人主动放弃）

### 1.2 返工规则

| 返工次数 | 处理方式 | 新状态 |
|---------|---------|--------|
| 第1次返工 | 保持原执行人，继续执行 | `in_progress` |
| 第2次返工 | 执行人任务失败，需重新选择执行人派发 | `failed` |

### 1.3 超时机制（**超时是状态属性，非独立状态**）

**设计原则**：超时状态通过计算得出，不存储为独立状态。超时信息作为 Task 的 `timeout` 属性。

#### 1.3.1 超时配置

```typescript
const OVERTIME_CONFIG = {
  // 阈值配置
  acceptWarningHours: 12,      // 接受超时预警：12小时
  acceptCriticalHours: 24,     // 接受超时危急：24小时
  executionWarningHours: 24,    // 执行超时预警：24小时（预计时间80%时触发）
  acceptanceWarningHours: 24,   // 验收超时预警：24小时
  acceptanceCriticalHours: 48,  // 验收超时危急：48小时

  // 延期限制
  maxExtensions: 3,             // 最多延期3次
  maxExtensionHours: 72,      // 每次最多延期72小时
  totalMaxExtensionHours: 168, // 总计最多延期168小时

  // 催办限制
  reminderMinIntervalMinutes: 60,  // 催办间隔至少60分钟
  maxRemindersPerDay: 5,         // 每天最多催办5次
};
```

#### 1.3.2 超时判断逻辑

```typescript
// 超时检测（页面加载时 + 定时器触发）
function detectOvertime(task: Task): Task['timeout'] | undefined {
  const now = new Date();

  // 1. 接受超时检测（pending状态）
  if (task.status === 'pending') {
    const publishedAt = new Date(task.createdAt);
    const hoursDiff = (now - publishedAt) / (1000 * 60 * 60);
    if (hoursDiff >= OVERTIME_CONFIG.acceptCriticalHours) {
      return { type: 'accept', severity: 'critical', startedAt: task.createdAt, deadline: '' };
    }
    if (hoursDiff >= OVERTIME_CONFIG.acceptWarningHours) {
      return { type: 'accept', severity: 'warning', startedAt: task.createdAt, deadline: '' };
    }
  }

  // 2. 执行超时检测（in_progress状态）
  if (task.status === 'in_progress' && task.acceptedAt) {
    const deadline = new Date(task.acceptedAt);
    deadline.setHours(deadline.getHours() + (task.estimatedDays || 1) * 24);
    if (now > deadline) {
      return { type: 'execution', severity: 'critical', startedAt: task.updatedAt, deadline: deadline.toISOString() };
    }
  }

  // 3. 验收超时检测（waiting_acceptance状态）
  if (task.status === 'waiting_acceptance') {
    const submittedAt = new Date(task.updatedAt);
    const hoursDiff = (now - submittedAt) / (1000 * 60 * 60);
    if (hoursDiff >= OVERTIME_CONFIG.acceptanceCriticalHours) {
      return { type: 'acceptance', severity: 'critical', startedAt: task.updatedAt, deadline: '' };
    }
    if (hoursDiff >= OVERTIME_CONFIG.acceptanceWarningHours) {
      return { type: 'acceptance', severity: 'warning', startedAt: task.updatedAt, deadline: '' };
    }
  }

  return undefined;
}
```

#### 1.3.3 执行超时处理流程

当任务执行超时（`timeout.type === 'execution'`）时：
1. 页面显示超时警示
2. 执行人必须选择：
   - **继续执行**：填写超时原因 → 延期（新截止时间）
   - **放弃执行**：填写放弃理由 → 任务变为 `abandoned`

#### 1.3.4 延期记录

### 1.4 操作权限矩阵

**核心原则**：不同角色对任务有不同的操作权限。

```typescript
// 操作权限矩阵
const TASK_PERMISSIONS = {
  // 撤回：仅pending状态，管理员可操作
  withdraw: { roles: ['admin'], statuses: ['pending'] },

  // 取消：accepted/in_progress状态，管理员可操作
  cancel: { roles: ['admin'], statuses: ['accepted', 'in_progress'] },

  // 重新派发：failed/abandoned状态，管理员可操作
  reassign: { roles: ['admin'], statuses: ['failed', 'abandoned'] },

  // 接受任务：仅pending状态，执行人可操作
  accept: { roles: ['assignee'], statuses: ['pending'] },

  // 验收：waiting_acceptance状态，验收人（派发人/管理员）可操作
  verify: { roles: ['assigner', 'admin'], statuses: ['waiting_acceptance'] },

  // 继续执行：rejected状态，保持原执行人
  continue: { roles: ['assignee'], statuses: ['rejected'] },

  // 提交进度：accepted/in_progress状态，执行人可操作
  submitProgress: { roles: ['assignee'], statuses: ['accepted', 'in_progress'] },

  // 催办：所有状态，管理员可操作
  remind: { roles: ['admin'], statuses: ['*'] },
};

// 状态转换限制
const STATUS_TRANSITIONS = {
  draft: ['pending', 'cancelled'],
  pending: ['accepted', 'cancelled'],  // withdrawn撤回并入cancelled，取消操作
  accepted: ['in_progress', 'cancelled'],
  in_progress: ['waiting_acceptance', 'cancelled', 'abandoned'],
  waiting_acceptance: ['completed', 'rejected'],
  rejected: ['in_progress', 'failed'],
  failed: ['pending'],  // 重新派发
  abandoned: ['pending'],  // 重新派发
  cancelled: [],  // 终态
  completed: [],  // 终态
};
```

### 1.5 催办功能

#### 1.5.1 催办规则
- **催办间隔**：同一任务催办间隔需大于60分钟
- **每日上限**：同一任务每天最多催办5次
- **自动催办**：任务派发12小时后未接受可自动催办

#### 1.5.2 催办记录

```typescript
interface ReminderRecord {
  id: string;
  taskId: string;
  taskCode: string;
  remindedBy: string;       // 催办人
  remindedTo: string;       // 被催办人
  remindType: 'manual' | 'auto';
  message?: string;
  remindedAt: string;
  acknowledgedAt?: string;  // 被催办人确认时间
}
```

### 1.6 批量操作
- **批量派发**：选择多个任务/执行人，批量派发
- **批量验收**：选择多个已完成的任务，批量验收通过
- **批量重派**：选择多个超时任务，批量更换执行人

**取消功能（accepted/in_progress状态，管理员）**：
- 点击取消后，任务状态变为 `cancelled`
- 需填写取消原因
- 生成取消记录

**超时处理功能**：
- 当 `task.timeout?.severity === 'critical'` 时：
  - 执行人看到超时警示弹窗

**催办功能**：
- 催办后发送通知给执行人/验收人
- 记录催办时间（ReminderRecord）

**验证弹窗功能**：
1. 展示该任务的所有操作记录（TaskRecord列表）
2. 每条记录显示：提交人、时间、进度、内容（文字/图片/语音）
3. 两个按钮：通过（完成任务）/ 返工（填写理由）

### 4.3 存储容量管理

```typescript
// dataManagement.ts

const DATA_MANAGEMENT = {
  // 操作记录保留策略
  taskRecords: {
    maxPerTask: 100,        // 每个任务最多100条记录
    archiveAfterDays: 90,   // 90天后归档
  },

  // localStorage 容量监控
  storageMonitor: {
    warnThreshold: 0.8,     // 80%时警告
    criticalThreshold: 0.95, // 95%时清理旧数据
  },
};

// 存储容量检查
function checkStorageCapacity(): { used: number; available: number; percentage: number } {
  let used = 0;
  for (const key in localStorage) {
    if (localStorage.hasOwnProperty(key)) {
      used += localStorage.getItem(key)?.length || 0;
    }
  }
  const limit = 5 * 1024 * 1024; // 5MB
  return { used, available: limit - used, percentage: used / limit };
}

// 分批处理大量数据的辅助函数
async function processInBatches<T>(
  items: T[],
  processor: (item: T) => Promise<void>,
  batchSize: number = 50
): Promise<void> {
  for (let i = 0; i < items.length; i += batchSize) {
    const batch = items.slice(i, i + batchSize);
    await Promise.all(batch.map(processor));
    await new Promise(resolve => setTimeout(resolve, 10)); // 让出主线程
  }
}
```

## 十、风险与注意事项

### 10.1 数据兼容性
- 现有任务数据的 `status` 字段需要检查是否能映射到新状态
- 现有临时任务数据需要迁移到统一Task模型
- 建议：迁移前先备份localStorage数据
- TaskRecord 统一后，原有的 TaskFlowRecord 和 TaskOperationRecord 需要数据迁移

### 10.2 功能影响范围
- 每日工单汇总改造可能影响现有数据的展示，需做好数据映射
- 超时检测需要在页面加载和定时触发，需考虑性能
- 操作记录数据量增加，需考虑分页或虚拟滚动

### 10.3 超时机制注意事项
- 接受超时检测频率：页面加载时检测 + 定时器每5分钟检测
- 催办间隔限制：同一任务催办间隔需大于60分钟（REMINDER_CONFIG.minIntervalMinutes）
- 超时状态变更需要记录到 TaskRecord 中
- 延期次数和总时长受 DEADLINE_CONFIG 限制

### 10.4 权限控制
- 撤回/取消操作：仅管理员可操作
- 验收操作：仅验收人（派发人或管理员）可操作
- 重新派发：仅管理员可操作
- 所有权限控制在前端实现，后端需同步校验

### 10.5 技术风险

#### localStorage 容量风险
- 操作记录会持续增长，可能触及 5MB 限制
- 建议：实现存储容量监控（storageManager），80%时警告，95%时清理旧数据

#### 性能风险
- useOvertimeDetection 每次页面加载遍历所有任务
- 大量操作记录渲染可能卡顿
- 建议：分批处理（batchSize=50）、使用虚拟滚动

#### 并发冲突（预留）
- 当前为单用户场景
- 后续多用户时需要乐观锁（version字段）

### 10.6 消息通知（后续扩展）
- 催办提醒可集成消息通知系统
- 任务超时可发送邮件/短信通知
- 任务状态变更可通知相关人员

## ADR (Architecture Decision Record)

### Decision 1: 统一操作记录模型

**问题**：原方案定义了 TaskFlowRecord 和 TaskOperationRecord 两个相似的操作记录类型，功能重复且维护困难。

**决策**：统一为 TaskRecord 接口，记录所有任务操作行为。

**理由**：
- 减少数据冗余
- 统一数据结构便于查询和展示
- feedback 字段统一设计支持多种反馈类型

**后果**：需要迁移原有的 TaskFlowRecord 和 TaskOperationRecord 数据。

---

### Decision 2: 超时作为状态属性而非独立状态

**问题**：原方案将 `overtime_pending`、`overtime_executing` 作为独立状态，导致状态数量膨胀且逻辑混乱。

**决策**：超时信息作为 Task 的 `timeout` 属性（包含 type/severity/startAt/deadline），不作为独立状态。

**理由**：
- 状态机更简洁清晰（9种状态 vs 12种）
- 超时是临时状态，不应与正常状态并列
- UI 通过 timeout.severity 展示不同级别警示

**后果**：需要更新超时检测逻辑和 UI 渲染逻辑。

---

### Decision 3: 操作权限矩阵控制

**问题**：原方案未明确操作的权限控制。

**决策**：通过 TASK_PERMISSIONS 配置矩阵，明确每个操作的角色和状态限制。

**理由**：
- 权限控制更清晰
- 便于后续扩展角色
- 前端后端可共享同一配置

**后果**：需要实现权限校验函数 canPerformAction()。

---

### Decision 4: 延期限制配置

**问题**：原方案未限制延期次数和时长。

**决策**：通过 DEADLINE_CONFIG 配置延期限制（最多3次，每次最多72小时，总计最多168小时）。

**理由**：
- 防止无限延期
- 与业务实际约束匹配
- 配置化便于调整

**后果**：延期操作时需检查配置限制。

---

### Decision 5: 催办功能完整设计

**问题**：原方案催办功能过于简单。

**决策**：实现完整的催办机制（间隔60分钟、每日最多5次、自动催办、催办记录）。

**理由**：
- 防止骚扰被催收人
- 记录可追溯
- 可扩展自动催办

**后果**：需要新增 ReminderRecord 和 useReminder Hook。

---

### Decision 6: 存储容量管理

**问题**：操作记录持续增长可能触及 localStorage 5MB 限制。

**决策**：实现 storageManager 工具（容量监控、分批处理、归档策略）。

**理由**：
- 防止数据丢失
- 监控可预警
- 归档策略保留历史数据

**后果**：需要定期检查和清理旧数据。
