# 农事任务派发流程重构规划

## Context

农事管理模块现有5个子模块，任务是核心数据闭环节点。目前存在以下问题：
1. 农事任务派发流程缺少完整的验收和返工机制
2. 临时任务位于任务中心而非统一的任务派发管理
3. 任务数据未形成完整的闭环：任务派发 → 执行 → 进度提交 → 工单汇总
4. 各页面数据字段不统一，追溯困难

**目标**：以现有农事任务派发表格数据为基础，统一其他页面数据字段，实现任务全生命周期管理和数据闭环。

## 一、任务状态流转设计

### 1.1 完整状态定义

```
[草稿] → [已发布] → [已接受] → [处理中] → [待验收] → [已完成]
   ↓           ↓           ↓          ↓
 [取消]    [超时待重派] [超时未开始] [超时未提交]
                          ↓
                      [放弃执行] → [待重派]
```

**状态枚举**：
- `draft` - 草稿（未发布）
- `pending` - 已发布（待接受）
- `accepted` - 已接受（开始处理）
- `in_progress` - 处理中（执行人正在执行）
- `waiting_acceptance` - 待验收（执行人提交100%完成）
- `completed` - 已完成（验收通过）
- `rejected` - 返工中（验收驳回，等待继续执行）
- `failed` - 任务失败（超过2次返工，需重新派发）
- `cancelled` - 已取消
- `overtime_pending` - 超时待重派（接受超时）
- `overtime_executing` - 执行超时（未按时完成）
- `abandoned` - 已放弃（执行人主动放弃）

### 1.2 返工规则

| 返工次数 | 处理方式 | 新状态 |
|---------|---------|--------|
| 第1次返工 | 保持原执行人，继续执行 | `in_progress` |
| 第2次返工 | 执行人任务失败，需重新选择执行人派发 | `failed` |

### 1.3 超时机制

#### 1.3.1 接受超时（pending状态）
- **定义**：任务派发后，执行人在设定时间内未接受
- **默认阈值**：24小时
- **处理流程**：
  1. 超过阈值后，状态变为 `overtime_pending`
  2. 农事任务派发页面显示警示标记
  3. 管理员可选择：重新派发给原执行人 / 更换执行人派发 / 取消任务

#### 1.3.2 执行超时（in_progress状态）
- **定义**：任务接受后，执行人未在预定时间内完成
- **计算方式**：当前时间 > 计划结束时间（acceptedAt + estimatedDays）
- **处理流程**：
  1. 超过预定时间未100%提交，状态变为 `overtime_executing`
  2. 页面显示警示标记，提醒执行人补充超时原因
  3. 执行人需要选择：
     - **继续执行**：填写超时原因说明，选择新的预计完成时间
     - **放弃执行**：填写放弃理由，任务变为 `abandoned`，待重新派发

#### 1.3.3 验收超时（waiting_acceptance状态）
- **定义**：执行人提交完成，验收人在设定时间内未验收
- **默认阈值**：48小时
- **处理流程**：
  1. 超过阈值后，显示验收超时警示
  2. 自动发送催办提醒给验收人

### 1.4 其他业务流程

#### 1.4.1 任务撤回（仅限pending状态）
- **条件**：任务派发后，执行人未接受前
- **操作**：管理员可撤回任务，状态变为 `cancelled`
- **影响**：任务从执行人任务列表移除

#### 1.4.2 任务取消（处理中也可取消）
- **条件**：任务执行过程中，管理员可取消
- **操作**：填写取消原因，状态变为 `cancelled`
- **影响**：任务结束，生成取消记录

#### 1.4.3 催办提醒
- **触发时机**：
  - 任务派发超过12小时未接受
  - 任务执行超过预定时间50%未提交任何进度
  - 任务待验收超过24小时
- **提醒方式**：页面红色警示 + 消息通知

#### 1.4.4 批量操作
- **批量派发**：选择多个任务/执行人，批量派发
- **批量验收**：选择多个已完成的任务，批量验收通过
- **批量重派**：选择多个超时任务，批量更换执行人

**超时检测机制**（定时任务或页面加载时检测）：

```typescript
// useOvertimeDetection.ts
function checkOvertime(tasks: Task[]) {
  const now = new Date();

  tasks.forEach(task => {
    // 1. 接受超时检测（pending状态）
    if (task.status === 'pending') {
      const publishedAt = new Date(task.updatedAt);
      const hoursDiff = (now - publishedAt) / (1000 * 60 * 60);
      if (hoursDiff > OVERTIME_CONFIG.pendingAcceptHours) {
        updateTask(task.id, { overtimeStatus: 'pending_accept' });
      }
    }

    // 2. 执行超时检测（in_progress状态）
    if (task.status === 'in_progress' && task.acceptedAt) {
      const deadline = calculateDeadline(task.acceptedAt, task.estimatedDays);
      if (now > deadline && task.progress < 100) {
        updateTask(task.id, {
          overtimeStatus: 'executing',
          overtimeAt: now.toISOString()
        });
      }
    }

    // 3. 验收超时检测（waiting_acceptance状态）
    if (task.status === 'waiting_acceptance') {
      const submittedAt = new Date(task.updatedAt);
      const hoursDiff = (now - submittedAt) / (1000 * 60 * 60);
      if (hoursDiff > OVERTIME_CONFIG.waitingAcceptanceHours) {
        updateTask(task.id, { overtimeStatus: 'waiting_acceptance' });
      }
    }
  });
}
```

## 十、风险与注意事项

### 10.1 数据兼容性
- 现有任务数据的 `status` 字段需要检查是否能映射到新状态
- 现有临时任务数据需要迁移到统一Task模型
- 建议：迁移前先备份localStorage数据

### 10.2 功能影响范围
- 每日工单汇总改造可能影响现有数据的展示，需做好数据映射
- 超时检测需要在页面加载和定时触发，需考虑性能
- 操作记录数据量增加，需考虑分页或虚拟滚动

### 10.3 超时机制注意事项
- 接受超时检测频率：建议页面加载时检测 + 定时器每5分钟检测
- 催办间隔限制：同一任务催办间隔需大于1小时
- 超时状态变更需要记录到操作记录中

### 10.4 权限控制
- 撤回/取消操作：仅管理员或任务创建人可操作
- 验收操作：仅验收人（通常是派发人或指定验收人）可操作
- 重新派发：仅管理员可操作

### 10.5 消息通知（后续扩展）
- 催办提醒可集成消息通知系统
- 任务超时可发送邮件/短信通知
- 任务状态变更可通知相关人员

## ADR (Architecture Decision Record)

### Decision: 统一任务管理模式

### Drivers
- 农事任务派发和临时任务需要统一管理
- 任务执行进度需要完整追踪
- 数据需要形成闭环，支持统计和分析

### Alternatives Considered
1. **保持现状**：各模块独立管理任务，但数据闭环难以实现
2. **完全重构**：重写所有任务相关代码，风险高周期长

### Why Chosen
- 以现有农事任务派发表格数据为基础，改动风险可控
- 统一数据模型后可实现完整的数据闭环
- 符合用户"不修改现有表格数据"的要求

### Consequences
- 需要修改多个页面的数据来源
- 临时任务数据需要迁移
- 操作记录的数据量会增加，需考虑存储优化

### Follow-ups
- 评估操作记录的存储容量，必要时做数据归档策略
- 考虑后续是否需要任务超时自动提醒功能
