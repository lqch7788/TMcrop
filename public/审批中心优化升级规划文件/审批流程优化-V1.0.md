## 一、项目背景与目标

### 1.1 背景

种植管理系统目前已构建审批中心（Approval Center），支持以下审批类型：

- **业务审批**：领料单、采购申请、生产计划、采收申请、退料单
- **HR审批**：请假、加班、离职、招聘、入职、考勤补录、调薪、合同续签、工资预算、转岗

然而，系统中大量核心业务模块尚未与审批中心对接，导致以下问题：

1. **数据孤岛**：业务操作与审批流程分离，状态不同步
2. **责任不清**：关键业务操作缺乏审批留痕，无法追溯
3. **风险控制不足**：种源入库、订单创建、任务派发等关键操作无审批管控
4. **用户体验差**：各模块自行管理状态，与审批中心状态不一致

### 1.2 目标

全面梳理种植管理系统所有业务流程，识别需要审批的环节，补充缺失的审批流程，实现所有审批业务与审批中心的无缝对接。

## 五、审批流程详细设计

### 5.1 种源入库审批流程

#### 业务说明
种源入库是种源管理模块的核心操作，记录种子/种苗的采购信息，涉及资金支出和库存增加。

#### 流程图
详见 `种植管理系统审批流程图.drawio` → "种源入库审批流程"

#### 流程步骤

```
1. 申请人填写种源入库单
   ├── 作物信息（从品种库选择）
   ├── 供应商信息
   ├── 采购数量和单价
   ├── 采购日期
   └── 上传图片凭证

2. 提交审批
   ├── 生成审批单（ApprovalType: SEED_SOURCE_INBOUND）
   ├── 关联种源记录ID
   └── 种源状态设为"待审批"

3. 审批节点
   ├── 一级：部门负责人（审核采购必要性）
   ├── 二级：财务审核（审核预算和金额）
   └── 三级：总经理（大额采购终审，>5000元）

4. 审批结果处理
   ├── 通过：
   │   ├── 种源状态更新为"已入库"
   │   ├── 创建作物实例
   │   └── 库存增加
   └── 拒绝：
       ├── 种源状态更新为"已拒绝"
       └── 通知申请人
```

#### 数据结构设计

```typescript
// 新增审批类型
SEED_SOURCE_INBOUND = 'seed_source_inbound'

// BusinessLink 扩展
interface BusinessLink {
  // ... 已有字段
  seedSourceId?: string;        // 种源记录ID
  seedSourceCode?: string;      // 种源批号
  supplierId?: string;          // 供应商ID
  purchaseAmount?: number;      // 采购金额
  quantity?: number;            // 数量
  unit?: string;                // 单位
}
```

### 5.2 订单创建审批流程

#### 业务说明
订单管理涉及销售合同，直接影响公司收入和客户需求，必须经过审批确保订单条款合理、价格正确。

#### 流程步骤

```
1. 销售人员填写订单
   ├── 客户信息
   ├── 作物品种和数量
   ├── 单价和总金额
   ├── 交货日期
   └── 付款方式

2. 提交审批
   ├── 生成审批单（ApprovalType: ORDER_CREATE）
   ├── 关联订单ID
   └── 订单状态设为"待审批"

3. 审批节点
   ├── 一级：销售主管（审核客户信用和条款）
   ├── 二级：财务审核（审核价格和回款）
   └── 三级：总经理（大额订单终审，>10000元）

4. 审批结果处理
   ├── 通过：
   │   ├── 订单状态更新为"已确认"
   │   └── 创建关联生产计划（可选）
   └── 拒绝：
       ├── 订单状态更新为"已拒绝"
       └── 通知销售人员
```

### 5.3 任务派发审批流程

#### 业务说明
农事任务派发直接影响人员工作安排和生产执行，需确保任务合理性、人员匹配度。

#### 流程步骤

```
1. 任务派发人创建任务
   ├── 任务类型
   ├── 执行人员
   ├── 执行时间和温室
   ├── 任务内容
   └── 所需物料

2. 提交审批
   ├── 生成审批单（ApprovalType: TASK_DISPATCH）
   ├── 关联任务ID
   └── 任务状态设为"待审批"

3. 审批节点
   ├── 一级：生产主管（审核任务合理性）
   └── 二级：部门负责人（审核人员安排）

4. 审批结果处理
   ├── 通过：
   │   ├── 任务状态更新为"待接受"
   │   └── 通知执行人员
   └── 拒绝：
       ├── 任务状态更新为"已拒绝"
       └── 退回派发人
```

### 5.4 生产批次创建审批流程

#### 业务说明
生产批次是生产管理的核心，批次创建后将贯穿种源、育苗、种植、采收全生命周期。

#### 流程步骤

```
1. 生产计划员创建批次
   ├── 作物品种
   ├── 种植模式
   ├── 种植面积
   ├── 预计产量
   └── 责任人员

2. 提交审批
   ├── 生成审批单（ApprovalType: PRODUCTION_BATCH）
   ├── 关联批次ID
   └── 批次状态设为"待审批"

3. 审批节点
   ├── 一级：生产主管
   ├── 二级：技术审核
   └── 三级：总经理

4. 审批结果处理
   ├── 通过：
   │   ├── 批次状态更新为"计划中"
   │   └── 创建关联任务
   └── 拒绝：
       └── 批次状态更新为"已取消"
```

### 5.5 技术方案审批流程

#### 业务说明
技术方案指导具体作物的种植技术，是生产质量的重要保障。当前系统已有 `approveStatus` 字段但无审批中心对接。

#### 流程步骤

```
1. 技术员编制方案
   ├── 作物类型
   ├── 种植阶段
   ├── 技术要点
   └── 附件文档

2. 提交审批
   ├── 生成审批单（ApprovalType: TECH_SOLUTION）
   ├── 关联方案ID
   └── 方案状态设为"审核中"

3. 审批节点
   ├── 一级：技术主管
   ├── 二级：生产主管
   └── 三级：总农艺师

4. 审批结果处理
   ├── 通过：
   │   ├── 方案状态更新为"已发布"
   │   └── 关联批次可使用
   └── 拒绝：
       ├── 方案状态更新为"已驳回"
       └── 退回技术员修改
```

### 5.6 物料入库审批流程

#### 业务说明
物料入库是库存管理的第一步，需确保入库数量、质量、价格准确。

#### 流程步骤

```
1. 仓库管理员填写入库单
   ├── 物料信息
   ├── 供应商
   ├── 入库数量
   ├── 单价和金额
   └── 质检结果

2. 提交审批
   ├── 生成审批单（ApprovalType: MATERIAL_INBOUND）
   ├── 关联入库单ID
   └── 入库单状态设为"待审批"

3. 审批节点
   ├── 一级：仓库主管（审核数量和质量）
   └── 二级：财务审核（审核金额）

4. 审批结果处理
   ├── 通过：
   │   ├── 入库单状态更新为"已入库"
   │   └── 库存增加
   └── 拒绝：
       └── 入库单状态更新为"已拒绝"
```

## 七.五、批量审批设计（新增）

### 7.5.1 设计原则

**所有审批流程统一支持"单审"和"批审"两种模式。**

- 单审：对单个审批单进行通过/拒绝/部分通过操作
- 批审：对多个审批单一次性进行批量通过或批量拒绝操作
- 批量审批时，每个审批单独立执行业务联动，互不影响
- 批量操作结果需展示成功/失败明细，支持失败重试

#### 批量审批执行逻辑

```typescript
// 批量通过实现
const batchApprove = useCallback((ids: string[], comment?: string): BatchApprovalResult => {
  const result: BatchApprovalResult = {
    total: ids.length,
    success: 0,
    failed: 0,
    details: [],
  };

  for (const id of ids) {
    try {
      // 逐个执行审批通过
      const approval = state.approvals.find(a => a.id === id);
      if (!approval) {
        result.details.push({ id, code: '', success: false, status: approval.status, error: '审批单不存在' });
        result.failed++;
        continue;
      }

      // 检查权限
      const hasPermission = checkBatchApprovalPermission(approval);
      if (!hasPermission) {
        result.details.push({ id, code: approval.code, success: false, status: approval.status, error: '无权审批此单据' });
        result.failed++;
        continue;
      }

      // 执行业务联动
      executeApprovalIntegration('approved', approval, { comment });

      // 更新审批状态
      dispatch({ type: 'APPROVE', payload: { id, comment } });

      result.details.push({ id, code: approval.code, success: true, status: ApprovalStatus.APPROVED });
      result.success++;
    } catch (error) {
      result.details.push({ id, code: approval.code, success: false, status: approval.status, error: String(error) });
      result.failed++;
    }
  }

  return result;
}, [state.approvals]);
```

```typescript
function isBatchApprovalSupported(type: ApprovalType): boolean {
  const batchSupportedTypes: ApprovalType[] = [

    ApprovalType.PRODUCTION_PLAN,
    ApprovalType.HARVEST_REQUEST,
    ApprovalType.RETURN_MATERIAL,
    ApprovalType.SEED_SOURCE_INBOUND,
    ApprovalType.MATERIAL_INBOUND,
    ApprovalType.MATERIAL_TRANSFER,
    ApprovalType.ORDER_CREATE,
    ApprovalType.ORDER_CHANGE,
    ApprovalType.TASK_DISPATCH,
    ApprovalType.TASK_CHANGE,
    ApprovalType.INSPECTION_ISSUE,
    ApprovalType.ISSUE_RESOLVE,
    ApprovalType.PRODUCTION_BATCH,
    ApprovalType.BATCH_CHANGE,
    ApprovalType.BATCH_VOID,
    ApprovalType.SEEDLING_PLAN,
    ApprovalType.PLANTING_PLAN,
    ApprovalType.TECH_SOLUTION,
    ApprovalType.BUDGET_CREATE,
    ApprovalType.BUDGET_ADJUST,
    ApprovalType.LEAVE,
    ApprovalType.OVERTIME,
    ApprovalType.ATTENDANCE_REPAIR,
  ];
  return batchSupportedTypes.includes(type);
}

// 检查用户是否有批量审批权限
function checkBatchApprovalPermission(approval: Approval, userId: string, userRole: string): boolean {
  // 1. 检查审批类型是否支持批量
  if (!isBatchApprovalSupported(approval.type)) {
    return false;
  }

  // 2. 检查当前用户是否为当前审批节点审批人
  const currentApprover = approval.approvers.find(
    a => a.order === approval.currentStep && a.userId === userId && a.status === 'pending'
  );
  if (currentApprover) {
    return true;
  }

  // 3. 检查角色权限（如管理员可批量审批）
  if (userRole === 'admin' || userRole === 'supervisor') {
    return true;
  }

  return false;
}
```

### 7.5.5 批量审批与业务联动

批量审批时，**每个审批单的业务联动独立执行**，一个失败不影响其他审批单。

```
批量审批通过（3张种源入库单）
│
├── 审批单 SP2026001
│   ├── 更新审批状态 → APPROVED
│   ├── 种源状态更新 → 已入库
│   ├── 创建作物实例 → 成功
│   └── 库存增加 → 成功
│
├── 审批单 SP2026002
│   ├── 更新审批状态 → APPROVED
│   ├── 种源状态更新 → 已入库
│   ├── 创建作物实例 → 成功
│   └── 库存增加 → 成功
│
└── 审批单 SP2026003
    ├── 更新审批状态 → APPROVED
    ├── 种源状态更新 → 已入库
    ├── 创建作物实例 → 失败（编码冲突）
    └── 库存增加 → 跳过
    
结果：SP2026003 业务联动失败，需人工处理或重试
```

### 7.5.6 批量审批异常处理

| 异常场景 | 处理策略 | 用户反馈 |
|---------|---------|---------|
| 部分审批单权限不足 | 跳过无权限项，继续处理有权限项 | 结果页标注"无权审批" |
| 业务联动失败 | 审批状态已更新，但业务操作失败 | 结果页标注具体失败原因 |
| 审批单已被他人处理 | 跳过该单据 | 结果页标注"已被处理" |
| 网络中断（批量中） | 已处理的保留结果，未处理的中止 | 结果页展示已处理/未处理明细 |
| localStorage 写入失败 | 记录失败，提示用户刷新重试 | Toast 提示"存储异常" |


#### 发现的状态同步风险

## 七.七、基于分析的审批优化建议

### 7.7.1 架构层面优化

#### 建议 1：引入审批配置化机制

**现状问题**：审批流程硬编码在组件中，新增审批类型需要修改多处代码。

**优化方案**：
```typescript
// 审批流程配置表
interface ApprovalFlowConfig {
  type: ApprovalType;
  name: string;
  nodes: ApprovalNode[];
  batchSupported: boolean;
  partialApproveSupported: boolean;
  notificationEnabled: boolean;
  autoEscalationEnabled: boolean;
  timeoutHours: number;
}

// 所有审批流程统一从配置表读取
const approvalFlowConfigs: ApprovalFlowConfig[] = [
  {
    type: ApprovalType.MATERIAL_REQUEST,
    name: '领料申请',
    nodes: [
      { order: 1, role: 'department_head', name: '部门负责人' },
      { order: 2, role: 'warehouse_manager', name: '仓库管理员' },
    ],
    batchSupported: true,
    partialApproveSupported: true,
    notificationEnabled: true,
    autoEscalationEnabled: false,
    timeoutHours: 48,
  },
  // ... 其他配置
];
```

**收益**：新增审批流程只需添加配置，无需修改核心代码。

#### 建议 2：建立统一的状态同步总线

**现状问题**：审批状态与业务状态各自维护，容易出现不一致。

**优化方案**：
```
统一状态同步总线 (ApprovalSyncBus)
├── 审批状态变更 → 推送至业务模块
├── 业务状态变更 → 推送至审批中心
├── 冲突检测 → 自动标记异常
└── 日志记录 → 完整审计链
```

**收益**：确保审批状态与业务状态始终一致，支持问题追溯。

#### 建议 3：审批数据与业务数据解耦

**现状问题**：审批单直接嵌套业务数据（BusinessLink），导致审批数据结构臃肿。

**优化方案**：
```typescript
// 解耦后：审批单只存关联ID
interface Approval {
  id: string;
  type: ApprovalType;
  status: ApprovalStatus;
  businessId: string;        // 业务单据ID
  businessType: string;      // 业务类型
  // ... 审批元数据
}

// 业务数据由各自模块管理，通过 businessId 关联查询
```

**收益**：审批数据结构稳定，业务模块可独立演进。

### 7.7.2 流程层面优化

#### 建议 4：建立审批分级机制

**现状问题**：所有操作统一走审批，小额/低风险操作也必填审批单。

**优化方案**：

| 审批级别 | 触发条件 | 审批节点 | 适用场景 |
|---------|---------|---------|---------|
| 免审批 | 金额 < 500 元 且 数量 < 10 | 无 | 小额领料、日常用品采购 |
| 快速审批 | 金额 < 2000 元 | 1级（直属上级） | 常规采购、标准任务派发 |
| 标准审批 | 金额 < 10000 元 | 2级（部门+财务） | 种源入库、订单创建 |
| 严格审批 | 金额 ≥ 10000 元 | 3级（部门+财务+总经理） | 大额采购、大额订单 |

**收益**：减少不必要的审批，提升日常操作效率。

#### 建议 5：引入审批前置校验

**现状问题**：用户提交审批后才发现问题（如库存不足），浪费审批资源。

**优化方案**：
```
提交审批前自动校验：
├── 领料单：库存是否充足
├── 采购申请：预算是否充足
├── 订单创建：客户信用是否良好
├── 种源入库：供应商是否合规
└── 任务派发：人员是否可用
```

**收益**：减少无效审批提交，提升审批效率。

#### 建议 6：关键业务强制审批

**现状问题**：部分高风险业务（如种源入库、订单创建）目前无审批。

**优化方案**：

| 业务操作 | 当前状态 | 建议 | 优先级 |
|---------|---------|------|--------|
| 种源入库 | 直接入库 | **强制审批** | 🔴 P0 |
| 订单创建 | 直接创建 | **强制审批** | 🔴 P0 |
| 任务派发 | 直接派发 | **强制审批** | 🔴 P0 |
| 物料入库 | 直接入库 | **强制审批** | 🔴 P0 |
| 生产批次创建 | 直接创建 | **强制审批** | 🟡 P1 |
| 技术方案发布 | 直接发布 | **强制审批** | 🟡 P1 |
| 库存调拨 | 直接调拨 | **强制审批** | 🟡 P1 |

### 7.7.3 体验层面优化

### 7.7.4 安全层面优化

#### 建议 10：审批操作审计日志

**现状问题**：审批操作只有简单的记录数组，缺乏完整的审计能力。

**优化方案**：
```typescript
interface AuditLog {

  timestamp: string;
```

### 7.8.3 权限校验实现

```typescript
// 审批权限配置
interface ApprovalPermissionConfig {
  type: ApprovalType;
  nodes: Array<{
    order: number;
    role: string;
    condition?: (approval: Approval) => boolean;  // 条件审批（如金额阈值）
  }>;
}

// 权限校验函数
function checkApprovalPermission(
  approval: Approval,
  userId: string,
  userRole: string,
  userDepartment: string
): { canApprove: boolean; nodeOrder?: number; reason?: string } {
  // 1. 获取审批类型配置
  const config = getPermissionConfig(approval.type);

  // 2. 查找当前待审批节点
  const currentNode = config.nodes.find(n => n.order === approval.currentStep);
  if (!currentNode) {
    return { canApprove: false, reason: '审批流程已结束' };
  }

  // 3. 校验角色权限
  if (currentNode.role !== userRole && userRole !== 'admin' && userRole !== 'general_manager') {
    return { canApprove: false, reason: '当前节点需要 ' + currentNode.role + ' 角色' };
  }

  // 4. 校验条件（如金额阈值）
  if (currentNode.condition && !currentNode.condition(approval)) {
    return { canApprove: false, reason: '不满足审批条件' };
  }

  // 5. 校验部门（部门负责人只能审批本部门）
  if (userRole === 'department_head' && approval.applicantDepartment !== userDepartment) {
    return { canApprove: false, reason: '只能审批本部门员工的申请' };
  }

  return { canApprove: true, nodeOrder: currentNode.order };
}
```

```typescript
// 通知服务
class ApprovalNotificationService {
  // 发送通知
  static send(notification: Omit<ApprovalNotification, 'id' | 'createdAt'>): void {
    const fullNotification: ApprovalNotification = {
      ...notification,
      id: 'NOTIF_' + Date.now(),
      createdAt: new Date().toISOString(),
    };

    // 1. 保存到 localStorage
    this.saveNotification(fullNotification);

    // 2. 更新 Badge 计数
    this.updateBadgeCount(notification.receiverId);

    // 3. 触发全局事件（供 UI 实时响应）
    window.dispatchEvent(new CustomEvent('approval-notification', {
      detail: fullNotification,
    }));
  }

  // 批量发送（如批量审批后通知多个申请人）
  static sendBatch(notifications: Omit<ApprovalNotification, 'id' | 'createdAt'>[]): void {
    notifications.forEach(n => this.send(n));
  }

  // 获取未读数量
  static getUnreadCount(userId: string): number {
    const notifications = this.getNotifications(userId);
    return notifications.filter(n => !n.isRead).length;
  }
}
```

```typescript
function getEffectiveApprover(approval: Approval, config: ApprovalPermissionConfig): string {
  const currentNode = config.nodes.find(n => n.order === approval.currentStep);
```

## 七.十二、数据迁移与兼容性方案

### 7.12.1 历史数据现状

系统中已存在大量历史业务数据（种源、订单、任务等），这些数据在创建时没有走审批流程，目前处于"直接生效"状态。

### 7.12.2 迁移策略

#### 策略："老数据默认已审批，新数据走新流程"

```
历史数据（新流程上线前创建）
├── 不生成补录的审批单（避免数据混乱）
├── 业务状态保持不变
└── 在页面上标注"历史数据（未走审批）"

新数据（新流程上线后创建）
├── 强制走审批流程
├── 审批通过后才生效
└── 状态与审批中心同步
```

### 7.12.3 兼容性处理

| 场景 | 处理方案 |
|------|---------|
| 历史种源记录 | 状态保持"已入库"，不补审批单 |
| 历史订单 | 状态保持"已确认"，不补审批单 |
| 历史任务 | 状态保持"已完成"，不补审批单 |
| 新增种源 | 必须先审批，审批通过后状态变为"已入库" |
| 修改历史订单 | 走"订单变更"审批流程 |
| 混合查询 | 列表页同时展示历史数据和待审批数据，用标签区分 |

### 7.12.4 localStorage 数据升级

```typescript
// 审批数据版本控制
const APPROVAL_DATA_VERSION = '2.0';

function migrateApprovalData(): void {
  const stored = localStorage.getItem(APPROVALS_STORAGE_KEY);
  if (!stored) return;

  const data = JSON.parse(stored);

  // 检查版本
  if (data.version === APPROVAL_DATA_VERSION) return;

  // v1 -> v2 迁移
  if (!data.version || data.version === '1.0') {
    // 1. 给所有历史审批单增加 batchSupported 字段（默认 false）
    data.approvals = data.approvals.map((a: Approval) => ({
      ...a,
      batchSupported: false,
    }));

    // 2. 更新版本号
    data.version = APPROVAL_DATA_VERSION;

    localStorage.setItem(APPROVALS_STORAGE_KEY, JSON.stringify(data));
  }
}
```

## 九、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 审批流程过于复杂，用户体验下降 | 高 | 提供"快速审批"模式，小额/低风险操作可设置免审批阈值 |
| 审批状态与业务状态不同步 | 高 | 统一状态管理，所有状态变更必须通过审批中心 |
| 审批节点人员缺失导致流程卡住 | 中 | 支持代理人设置，超时自动升级 |
| 历史数据迁移问题 | 中 | 历史数据默认标记为"已审批"，新流程仅对新数据生效 |
| 审批通知过多导致疲劳 | 低 | 支持批量审批、消息合并、免打扰设置 |
| **批量审批部分失败导致数据不一致** | **高** | **每个审批单独立执行业务联动，失败单据标记异常，支持单独重试** |
| **批量审批误操作（误点批量通过）** | **中** | **批量操作前强制确认弹窗，展示审批单明细列表，需二次确认** |
| **批量审批权限越界** | **中** | **严格校验每张单据的审批权限，无权限单据灰色不可选** |
